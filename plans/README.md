## Third pass: Go core plans (2026-07-29, same day)

Plans 018-038 turn every Go-core finding from the "Go core findings
(2026-07-29 pass)" section below into a plan, except DEP-02/03/04 (recorded
there as "checked, no action" — an environment limitation and two
no-findings, not defects). One plan (018) was written directly; the rest
(019-038) were written by six parallel forks, each independently verifying
every citation against the live `hiddify-core/` source before writing —
per this session's own standing rule that excerpts must come from a direct
read, not a subagent's report. That verification turned up several
corrections to the original audit pass, recorded here so they aren't lost:

- **SEC-01 is worse than first reported.** The original finding said desktop
  was uniquely insecure and mobile "already uses mTLS." Verifying it for
  plan 018 found the opposite: the one shared Dart call site
  (`lib/hiddifycore/hiddify_core_service.dart:94`) hardcodes
  `mode = 3` (`GRPC_NORMAL_INSECURE`) for every platform, and both
  `android/.../MethodHandler.kt:96` and `ios/.../MethodHandler.swift:85`
  hardcode an **empty** secret regardless of what Dart sends. Mobile's
  `MTLSChannelCredentials` branch in `core_interface_mobile.dart` is dead
  code — it's gated on `mode` values that are never actually passed. All
  three platforms are equally unauthenticated today. Plan 018 fixes all
  three; it deliberately does **not** attempt to finish the incomplete mTLS
  wiring (a larger, separate effort).
- **DEBT-04's dead code is scattered, not one block.** The original finding
  cited one contiguous commented-out range in `setRoutingOptions`. Plan
  034's verification found **9 separate dead-code regions**, not one — the
  plan's dead-code-deletion step (Step A) was rewritten around the real
  list.
- **DEP-01's commit count was undercounted from a truncated log.** The
  original finding estimated "~15 commits" from `git log --oneline -15`
  (i.e., it only ever looked at the last 15 commits — an artifact of the
  command, not the actual fork depth). Plan 038 found the actual
  upstream-sync boundary (`eac533ab`, "Merge upstream sing-box
  v1.14.0-alpha.14 into extended") and counted **92 commits** on top of it,
  including an unexplained block of ~20 upstream-commit reverts right after
  the sync point — flagged in plan 038 as worth a separate look, not
  something that plan fixes.
- **TESTCOV-04's gap is error-path coverage, not TLS-variant coverage.** The
  original finding said the shallow `ray2sing_test/` files lacked TLS/
  transport-variant coverage. Plan 032's verification found several of the
  named files (`vless_test.go`, `trojan_test.go`, `tuic_test.go`) already
  cover TLS variants — the real, confirmed gap across most of the 18
  protocol test files is malformed-input/error-path coverage. Plan 032 is
  scoped to that.
- **DEBT-01's Step 1 investigation resolved in favor of "fix it."** Plan 035
  was designed to check git history before assuming the commented-out
  fingerprint default in `xray_common.go` was a bug rather than a deliberate
  decision. It traces to that file's original creating commit
  (an unrelated commit message, "new: add xray fragment option") with no
  later commit ever explaining a deliberate removal — an oversight, not a
  settled decision. The plan proceeds with the fix.
- **A new, unplanned finding surfaced while writing plan 030's tests**:
  `static.HiddifyOptions` may be uninitialized on a fresh core instance,
  which could make `Restart`'s `EnableTun` check nil-pointer-panic. Plan
  030's Step 3 test is deliberately designed to surface this deterministically
  (via `recover()`); it instructs the executor to **report it as a new
  finding, not fix it** in that plan (fixing it belongs with plan 023's lock
  discipline work, which touches the same `HiddifyOptions` field). Whoever
  picks up plan 030 should watch for this and file a follow-up if confirmed.

**Verified directly, became plan 006**: the proxy-list gRPC stream terminates
permanently when the core is slow to start — `MakeSureContextIsNew`
(`hiddify-core/v2/hcore/commands.go:84-99`) waits at most 10 × 500 ms = 5 s,
after which `AllProxiesInfoStream` (`v2/hcore/proxy_info.go:189-248`) skips its
whole body and returns `E.New("hiddify service not found")`; the Dart client
(`lib/hiddifycore/hiddify_core_service.dart:298-316`) rethrows into
`handleExceptions`, whose `onErrorReturnWith` completes the stream for good.

**Verified directly, NOT planned — monitoring startup amplification**:
`hiddify-sing-box/common/monitoring/outbound_monitoring.go` uses
`defaultWorkerCount = 10` (`:37`), `defaultURLTestTimeout = 5s` (`:39`), and
all non-group outbounds start `invalid: true`, so the first cycle tests every
one. `runCycle` (`:636-662`) loops over `m.urls` and, when a stage yields zero
successes, re-tests the **entire** tag list against the next fallback URL.
`ConnectionTestUrls` defaults to 4 URLs (`v2/config/builder.go:250`). For ~45
outbounds pointing at one unreachable server that is 45 × 4 = 180 tests at 10
concurrent × 5 s ≈ **90 seconds** of churn, all aimed at a single host. This
does **not** block the proxy list (the immediate `stream.Send` at
`proxy_info.go:196` proves it), so it is load and battery cost rather than the
slow-list cause. Worth its own plan; retry only the failed tags rather than the
whole list.

**NOT audited at all** (agents died before producing findings): the Go core's
security posture — in particular whether the Go side enforces the generated
secret on the loopback gRPC control channel, and the trust boundary of the two
elevated helper processes (`v2/hcore/tunnelservice/` on port 18020,
`v2/hcore/icmpservice/` on 18021). The Dart side connects with
`ChannelCredentials.insecure()` and never sends the secret it generates; whether
that is exploitable depends entirely on the Go side, which remains unread. Also
unaudited: `ray2sing`'s link parsers (including the Shadowsocks-2022/EIH path,
still the unexplained "SS2022 doesn't work in proxy mode" report), and general
lifecycle/state correctness in `v2/hcore`.

### Security

- **[SEC-01] gRPC control server has no per-RPC authentication.** A `secret`
  field is plumbed end-to-end from the Dart/mobile callers into
  `SetupRequest` (`v2/hcore/hcore.proto:70`), but `Setup()`
  (`v2/hcore/grpc_server.go:41-127`) never reads it, and no auth interceptor
  is registered anywhere. Every real call site uses an insecure gRPC mode
  (`cmd/cmd_hiddify_run.go:34`, `v2/hcore/standalone.go:187`), so mTLS is
  configured but dead in practice. Net effect: any local process that can
  reach the listen address can call every RPC — start/stop the VPN, change
  settings, select outbound — with zero authentication. **Confirmed directly
  in this pass — and worse than described here; see the corrected writeup in
  plan 018 itself, all 3 platforms are affected, not just desktop.**
  **→ planned as [018](018-grpc-control-channel-authentication.md).**
- **[SEC-02] Elevated Tunnel helper (127.0.0.1:18020, runs as a persistent
  Windows service) accepts unauthenticated commands to redirect all system
  traffic.** `tunnel_platform_service.go:20-44` runs as `"HiddifyTunnelService"`
  via `kardianos/service` with no TLS/auth; its `Start` RPC
  (`tunnel_service.go:22-105`) takes caller-supplied server/port/credentials
  and builds a system-wide TUN adapter (`AutoRoute: true`) pointed at
  whatever the caller specifies — not restricted to hiddify's own proxy.
  `Exit` (`:131-142`) unauthenticated `os.Exit(0)`s the elevated process. Any
  unprivileged local process can hijack all machine traffic without a UAC
  prompt (the service is already elevated), or DoS it via `Exit`.
  **Confirmed directly in this pass.**
  **→ planned as [019](019-tunnel-helper-service-authentication.md).**
- **[SEC-03] Elevated ICMP helper (127.0.0.1:18021) has the same
  unauthenticated-loopback pattern** — `icmp_platform_service.go:65-87`, raw
  ICMP socket access for any local caller plus an unauthenticated `Exit`.
  Same fix pattern as SEC-02, smaller blast radius.
  **→ planned as [020](020-icmp-helper-service-authentication.md).**
- **[SEC-04] `ray2sing` Shadowsocks parser silently falls back to `method:
  "none"` (no encryption) instead of erroring on a malformed/password-less
  `ss://` link** (`ray2sing/ray2sing/shadowsocks.go:16-22`). Plausible root
  cause for the standing "SS2022 doesn't work in proxy mode" report — a
  silent security downgrade rather than a loud failure, not a confirmed fix
  for that report.
  **→ planned as [021](021-shadowsocks-parser-silent-downgrade.md).**

### Correctness

- **[CORRECTNESS-01] `GetSystemInfoStream` has the same "dies permanently if
  core is slow to start" shape as the already-fixed proxy-list bug** —
  `commands.go:100-113`, no retry, single terminal error.
  **→ planned as [022](022-fix-systeminfo-stream-init-wait.md)** (turned out
  to need a Dart-side fix — `watchStats` lacked the wait-for-init guard

- **[CORRECTNESS-02] `HiddifyInstance.StartedService`/`HiddifyOptions` are
  only sometimes guarded by `static.lock`** — real data-race pattern:
  `StopAndAlert` (`custom.go:14-21`), `buildconfighelper.go` handlers, and
  read paths in `commands.go`/`proxy_info.go` all touch these fields without
  the lock that `Start`/`Stop` take. Best case stale reads, worst case a Go
  data race / use-after-close.
  **→ planned as [023](023-hiddifyinstance-lock-discipline.md).**
- **[CORRECTNESS-03] Unguarded `grpcServer` map read in `Close`**
  (`pause.go:11-23`) racing against the mutex-guarded writes elsewhere in
  `grpc_server.go` — can crash the process (`fatal error: concurrent map
  read and map write`), not just misbehave.
  **→ planned as [024](024-fix-unguarded-grpcserver-map-read.md).**
- **[CORRECTNESS-04] Unsynchronized read of the `ipMaps` cache** in
  `config/builder.go:1158` (write is correctly locked two lines later) — same
  concurrent-map-crash risk as CORRECTNESS-03.
  **→ planned as [025](025-fix-ipmaps-race-and-dns-cache-shortcircuit.md)**

- **[CORRECTNESS-05] Nil pointer dereference in `DeleteProfile`/

## Findings recorded but NOT planned

### Security

- **Windows code-signing certificate is written to the workspace on PR-triggered
  runs.** `.github/workflows/build.yml:295-311` — the "Setup Windows Signing
  Properties" step is gated only on `startsWith(matrix.platform,'windows')`,
  **not** on `inputs.upload-artifact`, so a same-repo branch PR materializes the
  real PFX and its password into the workspace before PR-authored build scripts
  run (`:333-349`). Compounded by `permissions: write-all` (`ci.yml:30`,
  `build.yml:106`, `:461`, `:527`) and third-party actions pinned to mutable
  branches — `hiddify/signtool-code-sign-sha256@main` (`:353`) is handed the
  certificate. **Needs a maintainer decision** because it touches the release
  and signing pipeline, and because the correct response includes *rotating*
  the Windows signing certificate/password and the Android keystore
  credentials, not just re-gating the step.
- ~~**Unquoted executable path in Windows URL-protocol registration.**~~
  **→ planned as [009](009-quote-windows-protocol-executable-path.md).**
- **Android `allowBackup` is unset**, so the platform default (`true`) applies:
  `android/app/src/main/AndroidManifest.xml:27-34` has no `android:allowBackup`,
  `android:dataExtractionRules`, or `android:fullBackupContent`. Profiles
  (including subscription URLs, which embed per-user tokens) live in an
  unencrypted drift DB and plain files, so they are swept into Google account
  backup. One attribute; the trade-off (losing profile restore-on-reinstall) is
  a product call.
- ~~**Third-party git dependency pinned to `HEAD`.**~~
  **→ planned as [010](010-pin-installed-apps-git-dependency.md).**
- **Cleartext subscription fetches are silently allowed.**
  `lib/features/profile/data/profile_parser.dart:155-156` has a commented-out
  guard that used to reject `http://` subscription URLs. `dio_http_client.dart:129-152`
  lifts `uri.userInfo` into a `Basic` auth header, so over cleartext the
  subscription token is on the wire. The right fix is a warning-with-confirmation
  rather than a hard block (some providers legitimately serve cleartext) — which
  is a product decision.

## Findings considered and rejected

So nobody re-audits them:

- **Proxy list virtualization** — not a problem. `GridView.builder`,
  `SliverList.builder`, `ListView.builder` are used throughout; the only
  `ListView(children:)` sites are fixed-length settings pages.
- **N+1 database access** — none. `app_proxy_data_source.dart` uses
  `transaction()` / `db.batch()` and pushes filtering into SQL.
- **SQL injection** — drift's generated query builders throughout; the single
  raw statement (`lib/core/db/db.dart:73`) interpolates a compile-time table
  name, not user input.
- **Hardcoded credentials** — none found. The Sentry DSN is injected via
  `String.fromEnvironment` (`lib/core/model/environment.dart:7`); Android
  signing values come from a gitignored `key.properties`. The
  `"password": "admin"` at `json_editor.dart:219` is a UI schema example.
- **TLS bypass** — none. No `badCertificateCallback` anywhere; Android
  cleartext is correctly scoped to `127.0.0.1`
  (`android/app/src/main/res/xml/network_security_config.xml:3-5`); no iOS ATS
  exceptions.
- **README translation drift** — checked and not stale; all six were updated
  together on 2026-02-27 and carry matching heading counts.
- **`vclibs` looks unused but is load-bearing** — zero Dart references, but it
  is a Windows native plugin registered via
  `windows/flutter/generated_plugin_registrant.cc:17`. **Do not remove it**; a
  dependency-pruning pass would break Windows VC++ runtime provisioning
  silently.
- **26 direct `Platform.isX` sites bypass the `PlatformUtils` wrapper** — the
  wrapper only adds `!kIsWeb` guards and this app ships no web target.
  Cosmetic; not worth 26 edits.
- **`QUERY_ALL_PACKAGES` permission** (`AndroidManifest.xml:23-25`) — required
  by per-app proxy; conventional for this app class.
- **Route-rule Android app picker being fully commented out** — commit
  `7b6b203a` shows this was a deliberate deprecation in favour of
  `PerAppProxyPage`. Settled decision, not a finding (the dead code is worth
  deleting, which is a different category).
- **`protocol_handler` commented out of `pubspec.yaml`** — commit `b006ad92`
  shows a deliberate migration to `app_links`. Working as intended.
- **`lib/features/profile/details/json_editor.dart` (1699 lines)** — a
  deliberate vendored fork of `json_editor_flutter` 1.4.2 with protocol-specific

## Direction findings

Options for the maintainer, not defects. Effort here is a design/spike bracket,
deliberately coarser than the bug estimates above. Presented in the session
output rather than duplicated here; the four best-grounded were:

1. **Profiles are the one entity with import but no export** — config options,
   route rules, and per-app-proxy all ship symmetric clipboard+file
   import/export; profiles ship neither. Strong evidence, but any profile
   backup format holds subscription tokens, so passphrase encryption is a
   precondition, not a nice-to-have.
2. **An extension host already exists in the core with no client**
   (`android/app/src/main/protos/extension/extension_service.proto:11-18`,
   Dart stubs generated, zero consumers) — would let circumvention tactics ship
   without a store release. High risk: it is a server-driven-UI channel.
3. **Desktop `--start` / `--stop` flags are advertised and plumbed but dropped**
   — `linux/packaging/appimage/make_config.yaml:16-25` declares the actions,
   both native runners forward argv, and `lib/main.dart:7` declares
   `main()` with no `List<String> args`. Gated on fixing the desktop gRPC
   channel first (see below).
4. **The first-run free-config fetch is a single hardcoded GitHub URL with no
   fallback** (`lib/features/profile/notifier/profile_notifier.dart:191-199`),
   and `test.configs/README.md` documents the workaround in the maintainers' own
   words: you need another VPN for first-time use. Real friction at the funnel's
   front door — but every fallback added is a new fingerprintable callout from
   an unprotected device, so "better failure messaging + offline QR/file import"
   may beat "more network attempts".

Also surfaced and worth a maintainer decision on its own merits: **the desktop
gRPC control channel to the core is unauthenticated** —
`lib/hiddifycore/core_interface/core_interface_desktop.dart:74`, `:112` use
`ChannelCredentials.insecure()` and `SetupMode.GRPC_NORMAL_INSECURE`, a 100-char
`secret` is generated at `:66` and never sent, and the `MTLSChannelCredentials`
block is commented out at `:113-116`. Mobile *does* use mTLS
(`core_interface_mobile.dart:40-42`), so desktop is the outlier. Confirming
whether the Go core independently enforces the secret requires the submodule,
which was not available for this audit.
